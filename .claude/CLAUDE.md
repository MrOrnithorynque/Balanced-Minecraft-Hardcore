# Balanced Minecraft Hardcore (BMH)

Minecraft mod (mod id `bmh`) for Forge, Fabric and NeoForge: death sends you on a distant respawn instead of ending the run, the distance grows with the difficulty and the Eternal Items you carry. Author: MrOrnithorynque.

## Layout: one codebase, three loaders

Four Gradle modules (MultiLoader-Template style, all on official Mojang mappings):

- `common/`: the gameplay, vanilla code only. Its own build compiles it against vanilla Minecraft (VanillaGradle), so a loader import there fails the build. It ships no jar of its own (`common/build/libs` is a by-product, never published): each loader module compiles its sources and resources into their jars (root `build.gradle`), so each loader's mixin processor writes `bmh.refmap.json` for the common mixins too (except NeoForge, and Forge on 1.21.1, see Building).
- `forge/`: ForgeGradle 6 + MixinGradle, the `@Mod` class, `Config` (`config/bmh-common.toml`) and `forge/ForgeEvents` (Forge events, with the priorities the handlers rely on).
- `fabric/`: fabric-loom, the entrypoints, `FabricConfig` (`config/bmh.properties`) and `fabric/mixin`.
- `neoforge/`: ModDevGradle, `neoforge/BalancedMcHardcoreNeoForge` (`@Mod`), `NeoForgeConfig` (`config/bmh-common.toml`, same as Forge), `NeoForgeEvents` (same handlers and priorities as `ForgeEvents`) and the mixins config listed in its mods.toml (`neoforge.mods.toml` on 1.21.1). NeoForge runs on the official names since 1.20.2: no reobf, no refmap. It is built on 1.20.4 and 1.21.1: on the 1.20.x branches `settings.gradle` includes it only when `gradle.properties` has `neoforge_version` (only 1.20.4 does), and `mc-1.21.1` always includes it. NeoForge has no 1.20, its 1.20.1 is a Forge fork that loads the Forge jar as is (the release lists that jar for NeoForge too), and its 1.20.2 and 1.20.3 lines died young, so `neoforge/` sits unbuilt on those branches.

Common code reaches the loader through `platform/IPlatformHelper` (registration, creative tab builder, game rules, physical side, config), found with `ServiceLoader` (`META-INF/services` in each loader). Vanilla keeps `GameRules.register` private, so game rules go through it too.

Fabric hooks death, wake-up and item pickup with its own mixins rather than Fabric API events, to fire where Forge fires its events: `ALLOW_DEATH` runs before the totem check and `AFTER_DEATH` after the drops. No loader hooks the anvil or the enchanting table any more: the Navigator's Amulet used to take Unbreaking (a Fabric mixin mirrored Forge's `canApplyAtEnchantingTable`, 1.21.1 had a common `EnchantmentMixin` and a NeoForge `supportsEnchantment` override), and since it lost its durability it takes no enchantment, so the vanilla rules already say no.

A dedicated server must never load a client class: on Forge it refuses to start ("Attempted to load class ... for invalid dist DEDICATED_SERVER"; 1.1.0 and earlier did exactly that). Client code lives in `client/`, the client mixins and the loaders' client hooks, and stays out of the server's way: common code reaches it only behind `Services.PLATFORM.isPhysicalClient()`, the loader hooks are gated by `FMLEnvironment.dist` (Forge and NeoForge) and the `client` entrypoint (Fabric), and the mixins by the `client` list of their config. To start something on a client from the server, send a vanilla packet that a client mixin reads (`handlers/JourneySignal.java`): BMH has no network channel. `javap -v` on the built classes shows which ones reference `net/minecraft/client`.

## One branch per Minecraft version

The same mod ships for several Minecraft versions. Each version lives on its own long-lived branch, named `mc-<minecraft_version>`, except 1.20.4: `main` is the 1.20.4 branch (until 2026-11-06 the branches carried the Forge version, `dev-49.0.31` and so on, and 1.20.4 had a copy of `main` of its own). Everything under `common/src`, `forge/src`, `fabric/src` and `neoforge/src`, the build scripts other than `forge/build.gradle`, and the wrapper are identical on all the 1.20.x branches; `forge/build.gradle`, `gradle.properties`, `README.md` and `.vscode/settings.json` differ per branch (and `mods.toml` on `mc-1.20`).

`mc-1.21.1` is the exception: it has its own sources and build scripts, because 1.20.5 moved item data from NBT to data components and went to Java 21, 1.21 made enchantments registry data, made `ResourceLocation`'s constructor private (`fromNamespaceAndPath`) and renamed the data pack folders (`recipe/`, `loot_table/`, `tags/block/`, `tags/item/`: a tag in the old folder is silently empty), and Forge 1.20.6+ runs on the official names (no reobf, no refmap). Its port commit summarizes the differences; `git diff main mc-1.21.1` is the full list.

| Branch | Minecraft | Forge | Fabric API | NeoForge |
|---|---|---|---|---|
| `main` | 1.20.4 | 49.0.31 | 0.97.3+1.20.4 | 20.4.253 |
| `mc-1.20.3` | 1.20.3 | 49.0.2 | 0.91.1+1.20.3 | none |
| `mc-1.20.2` | 1.20.2 | 48.1.0 | 0.91.6+1.20.2 | none |
| `mc-1.20.1` | 1.20.1 | 47.2.0 | 0.92.12+1.20.1 | the Forge jar |
| `mc-1.20` | 1.20 | 46.0.14 | 0.83.0+1.20 | none |
| `mc-1.21.1` | 1.21.1 | 52.1.20 | 0.116.17+1.21.1 | 21.1.265 |

The table can drift: `gradle.properties` on each branch (`minecraft_version`, `forge_version`, `fabric_api_version`, `neoforge_version`) is the truth, except the 1.20.1 NeoForge cell: that is the release listing the Forge jar for NeoForge when `minecraft_version` is 1.20.1 (`.claude/skills/release/publish_local.py`).

**Every change goes to every branch, never to `main` alone.** Commit on `main`, then cherry-pick onto each `mc-*` branch (scratch worktrees work well), build each one, and push them together. `forge/build.gradle`, `gradle.properties` and `README.md` can conflict: keep the branch's own version of every line the change did not touch and apply only the change's hunks. Never take `main`'s whole file (`mc-1.20`'s `forge/build.gradle` has a different layout). After porting, `git diff --stat main <branch> -- . ':!forge/build.gradle' ':!gradle.properties' ':!README.md' ':!forge/src/main/resources/META-INF/mods.toml' ':!.vscode'` must be empty for every 1.20.x branch (`mc-1.20`'s `mods.toml` only lacks a commented-out template block).

On `mc-1.21.1` the cherry-pick applies cleanly only where the change does not touch the code 1.21 changed (items and their data, enchantments, `ResourceLocation` construction, data pack files, the loader hooks, the build scripts). Elsewhere, port the change by hand to the 1.21.1 API, build, and boot a server on each loader. The empty-diff check does not apply to it.

## Building

- No JDK is on the PATH; use Homebrew's: `JAVA_HOME=/opt/homebrew/opt/openjdk@17` on the 1.20.x branches, `JAVA_HOME=/opt/homebrew/opt/openjdk@21` on `mc-1.21.1`. The branch's `build.gradle` (`JavaLanguageVersion.of(...)`) says which; the release script reads it there too.
- `gradlew` has no exec bit in git: run `sh ./gradlew build` (every jar), or one loader: `sh ./gradlew :fabric:build`, `:forge:runClient`, `:neoforge:runServer`.
- Fast compile check of the shared code on every Minecraft version, no Gradle slot: `bash .claude/skills/verify-loaders/scripts/compile_check.sh [<version>...]` runs `javac` on `common/src/main/java` against each Loom jar. With no argument it reads `minecraft_version` in `gradle.properties`: a value starting with `1.21` gives `1.21.1`, anything else gives `1.20 1.20.1 1.20.2 1.20.3 1.20.4`. It proves the vanilla signatures exist, not that a mixin still hits its target, nor the loaders' code.
- The release jars land in `forge/build/libs/`, `fabric/build/libs/` and `neoforge/build/libs/`. The NeoForge jar never has a refmap (official names). The other two must contain `bmh.refmap.json`, and the Forge jar a `MixinConfigs` manifest entry, or the mixins will not load outside the dev environment. On `mc-1.21.1` the Forge jar has no refmap, on purpose: Forge 1.21.1 runs on the official names, and the annotation processor's refmap would point at SRG names that no longer exist at runtime (Mixin then logs that `bmh.refmap.json` could not be read, which is harmless).
- `runServer` needs `eula=true` in `<loader>/run/eula.txt`. Booting a dedicated server on each loader is the cheap check that registration, game rules, config and the client/server split hold. The first `runServer` of a loader in a fresh worktree also runs the plugin's setup, and a busy machine slows it (237 to 325 s seen): wait up to 15 minutes for `Done (` in the output, and read the log for it before trusting a timeout.
- `runClient` opens a plain `java` window that computer use cannot drive, but it runs unattended: write `<loader>/run/options.txt` (`onboardAccessibility:false`, `pauseOnLostFocus:false`, `soundCategory_master:0.0`), copy a world made by a dedicated server of the same version into `<loader>/run/saves/<name>` (an older world stops at a backup prompt), and run `sh ./gradlew :<loader>:runClient --args="--quickPlaySingleplayer <name>"` with a temporary client hook (switched on by an environment variable) that acts, saves frames with `Screenshot.grab(...)` queued by `Minecraft.tell(...)` and ends with `Minecraft.stop()`; the `verify-loaders` skill has one: the hook's copy in `common/src` is never committed, `branch.sh` copies it from `scripts/hook/`, which ships with the skill, into the verify worktree and removes it at the end. On NeoForge (ModDevGradle) `--args` replaces the whole command line, main class included: put the program arguments in the run config. Read `<loader>/run/logs/latest.log` for `[BalancedMcHardcoreMain]` lines. Judging looks and feel is still the user's.
- To check a branch on every loader with nobody at the keyboard (build, jar checks, a dedicated server and a quick-play client per loader, bots), use the `verify-loaders` skill: before a release and after porting a change to the version branches.

## Code map

Paths under `common/src/main/java/github/mrornithorynque/bmh/` unless stated.

- `handlers/RespawnPositionHandler.java`: the distant respawn (distance formula, safe landing spot). `mixin/F_PlayerListRespawnMixin.java` (common) asks it for the position inside vanilla's `PlayerList.respawn`, before vanilla sends any position to the client: the loader respawn events fire after that, and a teleport from there showed the spawn point first. The mixin differs per codebase: on 1.21.1 it changes the result of `findRespawnPositionAndUseSpawnBlock` (a `@ModifyVariable`, not a `@Redirect`, so other mods can change it too), on 1.20.x it moves the new player at the first `noCollision` check of `respawn` (one call site, in the loop that lifts the player out of blocks; a flag makes the mixin act once). Its targets are thousands of blocks from any player, in chunks that are not loaded: `Level.getHeight` then answers `minBuildHeight` and every spot looks like void, so load the chunk first (`serverLevel.getChunk(...)`). This broke every respawn once and compiled fine: verify respawn changes with a real death in `runClient` and its `[BalancedMcHardcoreMain]` log lines (`verify-loaders` has `death_client.sh` for that).
- `handlers/RespawnEffectHandler.java`: after a distant respawn, the bell and the respawn sound for the other players nearby, 200 ticks of damage immunity (`spawnInvulnerableTime` through `mixin/F_ServerPlayerAccessor.java`; vanilla gives 60) and the arrival signal.
- The journey cinematic of a distant respawn, client side: `client/journey/JourneyOverlay.java` (fade to black, night sky, message, pixel dissolve, then the bell; a vanilla `Overlay`, so it draws above the HUD and in place of the death and terrain screens, which still tick under it) and `client/journey/JourneyCinematic.java`. BMH has no network channel: `handlers/JourneySignal.java` sends vanilla title packets with `bmh.journey.*` keys (departure at death, before the death screen opens, and none for a death another mod cancels; arrival after the respawn; none in a hardcore world), and `mixin/F_GuiTitleMixin.java` (client list) takes them out before vanilla shows them. `mixin/F_LocalPlayerRespawnMixin.java` (client list) holds the Respawn button's request until the screen is black, and `mixin/F_MinecraftOverlayMixin.java` (client list) sends it at once when another overlay (a resource reload) replaces the journey: nothing else could, because `LocalPlayer.tickDeath` removes the client player 20 ticks after its death and the level ticks no removed entity.
- The Navigator's Amulet: `items/NavigatorAmuletItem.java` (sneak + use on a bed or lodestone opens the naming screen of a point, use at night under open sky reads the stars), `handlers/AmuletReading.java` (when the stars can be read, the charges, the reading it writes on the stack for the sky renderer: one azimuth and one name per point) and `handlers/AmuletPoints.java` (the named points, `maxAmuletPoints` in the mod config, saved on the player by `mixin/C_ServerPlayerMixin.java`; a Home from 1.5.0 to 1.6.x loads as a point named Home). Its needle is the client item property `client/AmuletCompass.java`, registered with the other client item properties in `client/ClientItemProperties.java` (every loader's client setup calls it); the model's 33 overrides switch on it. The naming screen uses no network channel: the server sends a `bmh.point.open` title (`handlers/AmuletPointSignal.java`, read by `mixin/F_GuiTitleMixin.java` through `client/amulet/PointSignal.java`, like the journey signals), `client/amulet/PointScreen.java` answers with the command `/bmh point save x y z <name>` or `/bmh point remove x y z` through `ClientPacketListener.sendUnsignedCommand`, and `handlers/AmuletPointCommand.java` checks everything a typed command could fake (amulet in hand, Overworld, a bed or lodestone within reach, a clean name, the cap, one change per second). `mixin/J_CommandsMixin.java` registers BMH's commands in the `Commands` constructor for every loader.
- `client/sky/` (`StarReadingRenderer` and its helpers) draws the amulet's star reading in the sky, called by `mixin/D_LevelRendererSkyMixin.java` (client list) right after vanilla's stars. Through a spyglass, `mixin/K_GuiSpyglassMixin.java` (client list) shows the name of the line whose last star the view aims at (`StarReadingRenderer.aimedName`): vanilla, Forge and NeoForge all draw the spyglass through `Gui.renderSpyglassOverlay(GuiGraphics, float)`. The sky pass culls back faces: wind triangles counter-clockwise as seen from the camera, like vanilla's star quads. An offline preview must cull the same way (`docs/redesign/sky-previews/SkyPreview.java` does), or it hides exactly those bugs.
- The Totem of Eternity: `handlers/TotemAwakeningHandler.java` turns a Dormant Totem plus an Echo Heart into it at the anvil for 39 levels, called from `mixin/B_AnvilMenuMixin.java` (common, no loader event). `mixin/A_LivingEntityTotemMixin.java` removes the Fire Resistance a Totem of Undying gives a player (a common mixin: Forge's totem event fires before the effects are added, Fabric has none).
- The Totem of Eternity's save and its limit: `handlers/TotemOfEternityHandler.java`. The second injection of `A_LivingEntityTotemMixin` calls `trySave` when no Totem of Undying in a hand saved a player: the first Totem of Eternity in the inventory saves them and turns into a Dormant Totem. `mixin/I_ClientPacketListenerTotemMixin.java` (client list) shows it in the totem animation. One per container: `mixin/I_SlotTotemMixin.java` (menus) and `mixin/I_ContainerTotemMixin.java`, which adds `canPlaceItem` to the container classes for hoppers (Mixin cannot inject into an interface default method; the build renames the added method, `jarcheck.py`'s `ADDED_METHODS` checks it). The player tick drops every Totem of Eternity after the first (`dropExtraTotems`), because a number key swap into the hotbar and a closed menu skip `Slot.mayPlace`.
- Eternal Items on the ground: `mixin/G_ItemEntityMixin.java` cancels their damage and, on the server only, gives them an unlimited lifetime (the client spins and bobs an item from its own age).
- The Eternal Sword has two sprites: 16x16 for the inventory, the ground and item frames, 20x20 in the hands. The item model's override on the client item property `bmh:in_hand` (`client/EternalSwordModel.java`) gives `eternal_sword_in_hand`, and `mixin/H_ItemRendererSwordMixin.java` (client list) asks for it when `ItemRenderer.render` draws a hand.
- The Eternal tools' abilities, all server side: `handlers/EchoStrikeHandler.java` (sword: an echo onto another enemy, queued on the player through `EchoStrikeQueue`), `handlers/AxeSmashHandler.java` (axe: a hit while falling hits harder) and `handlers/EchoSenseHandler.java` (pickaxe: the ores of `common/src/main/resources/data/bmh/tags/blocks/echo_sense_ores.json`, `tags/block/` on 1.21.1, glow through walls). The `mixin/E_*` classes feed them: `E_PlayerAttackMixin` (the hit), `E_ServerPlayerGameModeMixin` (the block break), `E_ServerPlayerMixin` (the queue and its clock), `E_DisplayMixin` with the two invokers (the glow displays) and `E_MinecraftServerMixin` (checks the ore tag at load). `items/EternalTooltips.java` holds the tooltip lines the Eternal Items share (heavy, ability or worn out, durability left with the 7% death wear). The tools never break: `handlers/EternalWear.java` keeps their last point of durability, through `mixin/L_ItemStackWearMixin.java` (`ItemStack.hurt` on 1.20.x, two `hurtAndBreak` methods on 1.21.1, because NeoForge routes the slot method around the player one). At that point a tool is worn out: half damage (`E_PlayerAttackMixin`), stone mining speed (the items' `getDestroySpeed`), no ability. A gold block repair at the anvil costs a flat 15 levels and keeps the prior work penalty (`B_AnvilMenuMixin`).
- Item `use()` and `useOn()`: both sides must agree on whether the click is consumed. `Minecraft.startUseItem` tries the main hand, then the off hand, and only a consuming result (or a FAIL from useOn) stops it. An item that decides on the server returns `InteractionResultHolder.consume(stack)` on the client (`level.isClientSide`) and the real result on the server, never `pass`: with `pass` the same click also uses the off-hand item (shield, bucket, ender pearl). `useOn` decides on both sides with the same test, or the client also sends `use()` for that click (`items/NavigatorAmuletItem.java` does both).
- `utilities/BMHGameRules.java`: the six BMH game rules; `ALL_RULES` is what the world creation toggle flips.
- `mixin/CreateWorldGameTabMixin.java`: the "Balanced Hardcore: ON/OFF" button on the Create New World screen, registered in `common/src/main/resources/bmh.mixins.json` (every loader; NeoForge lists it in its mods.toml). Fabric-only mixins are in `fabric/src/main/resources/bmh.fabric.mixins.json`. `forge/.../mixin/ForgeGuiMixin.java` is dead (body commented out, not registered; gone on `mc-1.21.1`). To add one, use the `add-mixin` skill.

## Writing style

Changelog entries and code comments you write or change use Simplified Technical English (ASD-STE100): short sentences (at most 25 words, 20 in a procedure), one idea per sentence, active voice, simple present tense, plain common words, the same word for the same thing, no idioms. Keep the articles (the, a). Example: "The totem no longer gives Fire Resistance." Do not rewrite old text only to change its style.

## Changelog

`CHANGELOG.md` at the repo root, same file on every branch. Any change a player could notice adds a line under `## [Unreleased]` in the same commit, written for players (what changed in game, not which class). Adding an item to a vanilla tag changes every reader of that tag, so scan the version's vanilla data and Java for it and give each player-visible reader a line (1.21.1: our tools sit in `swords`, `axes` and `pickaxes`, which `breaks_decorated_pots` reads, so they shatter decorated pots). A release turns that section into the version's entry (see the `release` skill), and the release posts exactly that entry as the changelog on CurseForge, the GitHub release and, for 1.21.1, Discord (see Releasing).

## Releasing

Use the `release` skill (`.claude/skills/release/SKILL.md`). Short version: bump `mod_version` and the changelog on every branch, build and verify every branch, tag each version branch `mc-<minecraft_version>-v<mod_version>` and push the tags, then run `.claude/skills/release/publish_local.py` on each built worktree: it uploads to CurseForge, creates the GitHub release and, for 1.21.1, posts the changelog to Discord, with the tokens from the macOS Keychain. GitHub Actions is off since 2026-11-05 (the account's Actions are locked over billing): both workflows sit in `.github/disabled-workflows/`, and no tag publishes by itself. Modrinth gets nothing for now (its token answered 401).
