## Consequence for a mod

In single player every server hook runs on the integrated server thread, and the owner is a guest of that hub. Nothing on the guest path filters the owner out.

- Death-cancel (`living_death`): RELIABLE for the owner (V2), when at least one mod is loaded.
- Respawn position (`player_respawn_position`): RELIABLE path (V1), a dimension change is honoured on the integrated thread; the hook comes from a pending fragment compiled into main (V1b, not proven by a build here). Present on the Nightly tag too.
- Item wear (`item_damaged`): RELIABLE (V3), not for a creative player.
- Damage (`living_incoming_damage`, v3): RELIABLE (V4).

- Inventory: `player_tick`, `inventory_tick`, `item_picked_up`, `loot_drops` at death RELIABLE for the owner (V5). `take_items`/`give_stack`/`give_levels` act on the owner inside the owner's own hook. From `server_tick` (no turn) a give to the owner is PLAUSIBLY refused on the integrated server (V6 trap): call it inside the owner's `player_tick`, or test it first.
- `server_players()` is empty inside any player hook; use `acting_player()` there.
- State: one mod instance and its statics are shared by the window and the server thread; use `Mutex`/atomics, keep server state apart by `window()`, and carry server facts to the client with mod messages or synced attachments. A `thread_local!` splits by thread.
