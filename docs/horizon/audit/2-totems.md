## 1. The save from death

### Behaviour spec (what the Java mod does)
- Trigger: `LivingEntity.checkTotemDeathProtection` returns false (no Totem of Undying in a hand saved the player), the entity is a ServerPlayer, and the damage is not in `DamageTypeTags.BYPASSES_INVULNERABILITY` (void, /kill still kill). mixin/A_LivingEntityTotemMixin.java:42-49.
- Then `TotemOfEternityHandler.trySave(player)` (handlers/TotemOfEternityHandler.java:29-58). It scans the whole inventory (`getContainerSize()`: main 36, armor 4, offhand) in slot order and takes the FIRST stack whose item is `TotemOfEternityItem` (:33-37). In that same slot it puts a new `ItemStack(DORMANT_TOTEM_OF_ETERNITY)` (:39). Then in order: `awardStat(ITEM_USED, totem)` (:40), `gameEvent(ITEM_INTERACT_FINISH)` (:41), `setHealth(1.0F)` (:43), `removeAllEffects()` (:44), Regeneration 900 ticks amplifier 1 (:45), Absorption 100 ticks amplifier 1 (:46), Fire Resistance 800 ticks amplifier 0 (:47) (the Fire Resistance stays: the nerf in the first injection only applies to the Totem of Undying), `broadcastEntityEvent(player, 35)` (:48), advancement `eternity/saved` (:49), a log line (:51).
- A Totem of Undying in a hand wins first (vanilla's check runs first): the injection runs on RETURN of the vanilla method.
- Totem of Undying nerf: the first injection (A_LivingEntityTotemMixin.java:28-36) removes `MobEffects.FIRE_RESISTANCE` from a PLAYER after vanilla's totem check returned true. Mobs keep vanilla's totem (class comment :17-19).
- Client: `I_ClientPacketListenerTotemMixin` (mixin/I_ClientPacketListenerTotemMixin.java:29-57) overrides `ClientPacketListener.findTotem(Player)` on RETURN: if a hand holds an item with `DEATH_PROTECTION` keep vanilla's; else the first `TotemOfEternityItem` in the inventory (copy) is shown; else, if a hand holds a `DormantTotemOfEternityItem`, show a fresh Totem of Eternity (this is the moon ritual's animation, whose new stack reaches the client after the event). The server sends the event before the Dormant Totem reaches the client, so the client still sees the Totem of Eternity.
- Item ids and data: see section 2. Lang keys for the tooltip line: `tooltip.bmh.totem_of_eternity_save` (en_us.json:15).
- Server side: all of it. Client side: only the findTotem override.

## 3. The awakening at the anvil and the gold block repair

### Behaviour spec
- Awakening (handlers/TotemAwakeningHandler.java:18-24, mixin/B_AnvilMenuMixin.java:64-78): at HEAD of `AnvilMenu.createResult`, if left = `bmh:dormant_totem` (Hollow) and right = `bmh:echo_heart`: `cost.set(39)`, `repairItemCountCost = 1`, result slot = fresh `ItemStack(totem_of_eternity)`, `broadcastChanges()`, cancel. `COST = 39` ("The most a survival anvil allows: 40 levels and above is Too Expensive", TotemAwakeningHandler.java:14). Name field is ignored (the result is fresh). A Dormant Totem (`sleeping_totem`) + Echo Heart gives nothing.
- Gold block repair (mixin/B_AnvilMenuMixin.java:80-113; handlers/EternalWear.java:27 `GOLD_REPAIR_COST = 15`, :69-72 `isGoldRepair(left, right)` = left is an Eternal sword/axe/pickaxe and right is `Items.GOLD_BLOCK`, :75-83 repair penalty = `DataComponents.REPAIR_COST`): at HEAD save the tool's penalty and set it to 0 (so vanilla never says Too Expensive); at RETURN restore the penalty on the tool AND on the result, `cost.set(15)`, `broadcastChanges()`. Vanilla's repair material loop decides the number of gold blocks used.
- `onTake` (:119-126): if the left slot holds an `IEternalItem`, empty it (guards Easy Anvils / Stackables, issue 5).

### Horizon mapping
- `prepare_anvil`, server, contract "replace" out "result", both catalogs. NH:6111-6117: `native_prepare_anvil(&mut self, player: u128, name: &str, pos: [i32; 3], result: &mut Option<ItemStack>, cost: &mut i32)`; DOC:1573: "change the result or level cost before it is sent to the menu. It has NO input arguments, and the player state is not swapped in, so the mod cannot read the left/right slots from it. ## 7. Client prediction of an item use (CLAUDE.md "Item use() and useOn()") and Horizon

### Java rule
.claude/CLAUDE.md "Item `use()` and `useOn()`": both sides must agree on whether the click is consumed. `Minecraft.startUseItem` tries the main hand, then the off hand, and only a consuming result (or a FAIL from useOn) stops it. An item that decides on the server returns `InteractionResultHolder.consume(stack)` on the client and the real result on the server, never `pass`: with `pass` the same click also uses the off-hand item (shield, bucket, ender pearl). `useOn` decides on both sides with the same test, or the client also sends `use()` for that click. In the Dormant Totem: `use()` returns CONSUME in every case (DormantTotemOfEternityItem.java:48-65).

### How Horizon handles it (evidence)
- SH/docs/native-hooks-neoforge.md rule 3 (:42-47): "Side. ... `both`: both, with the `Game`'s role available (`native_window`). Interactions are `both`: the client predicts, the server acts, and a mod that claims a use on one side only gets the two out of step."
- The use-over-time hooks follow it: `living_entity_use_item_start` NH:8236-8244: "Both sides, as vanilla's: on the server for every player of the world, and on a server's client for the uses it predicts. Answer the same on both, and change the world only on the server (`native_window` is false there), not on a server's client." Same sentence for tick, stop, release_using, on_use_tick ("Both sides ... change the world only where this `Game` runs the world").
- The client really predicts: remote.rs:8905-8932 sends `S::UseItem` and then "a mod's item used over time starts here too, as the server starts it", via `with_hand(hand, |g| g.start_mod_use(&held))`; for the claimed items case ("A mod's claimed item is never used on the server", remote.rs:8909-8911, DOC:1164 `native_claim_items`) the mod takes the whole click on the client only.
- `use_item` is `server` only ("claimed"), `use_item_on` has contract cancel/claimed with side unset in CAT (`use_item_on` side None, NIGHTLY too). DOC and NH:8197-8201: `use_item` "Server-side, for every player of the world".
- Consumption for the off-hand problem: `start_mod_use` returns true for any `mod_use` item once reached (use_hand.rs:300-303), so a refused start (hook cancel) still consumes the click: no off-hand double use, as Java's always-CONSUME. Horizon matches the rule by construction for this item. A mod item that is NOT a `mod_use` item (use duration 0) is handled differently (`use_item` claim).
- Difference to Java: the Java ritual starts on the server only. Horizon's client starts on its own prediction (rule 3), so the start predicate has to be client-computable (section 4 parity risks). Mitigation: answer `canceled = false` on the client (`native_window` true) and let the server decide, accepting a ritual shown for a moment on the client; how the client is told that the server never started the use: UNVERIFIED.

### Verdict
HOOK, with the desync risk above.
